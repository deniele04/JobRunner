| Campo | Contenido |
|---|---|
| **Identificador** | TC-018 |
| **Requisitos cubiertos** | Solicitudes duplicadas y desconexiones del cliente (decisión 8 de la minuta del 20/10/2026). RF/RNF: por confirmar contra el documento de requisitos y la numeración del PDF 05 (ver [matriz](../verification-plan/matriz-trazabilidad.md)) |
| **Objetivo** | Comprobar que reenviar un `submit` con el mismo `request_id` devuelve el mismo trabajo sin crear otro proceso, incluso tras una desconexión del cliente o un reinicio del servicio, y que un `request_id` inválido se rechaza. |

## Precondiciones
1. Linux (Ubuntu 22.04 / 24.04) o WSL2 con Python 3.10 o superior.
2. Repositorio clonado. No se requiere el servicio en ejecución ni dependencias externas.

## Pasos
| # | Acción |
|---|---|
| 1 | Desde la raíz del repositorio: `./scripts/setup.sh`. |
| 2 | Ejecutar la verificación: `verif/scripts/verify.sh <run-id>` (o `PYTHONPATH=src python3 -m unittest discover -s verif/unit -v`). |
| 3 | En `unittest.log`, comprobar el resultado de las pruebas listadas abajo. |

Pasos manuales equivalentes: con el servicio en ejecución, `royito submit --request-id r1 sleep 60` dos veces; `list` debe mostrar un solo trabajo y ambos envíos el mismo `id`.

## Resultado esperado
- Un `request_id` repetido devuelve el mismo `id` y no crea otro proceso ni otra fila en la base de datos.
- Si el cliente se desconecta antes de recibir la respuesta, la solicitud se aplica una sola vez y reenviarla devuelve el mismo trabajo.
- El duplicado también se detecta después de reiniciar el servicio.
- Un `request_id` vacío o que no es texto se rechaza con un mensaje de error y no crea ningún trabajo.
- Los envíos sin `request_id` siempre crean trabajos nuevos.
