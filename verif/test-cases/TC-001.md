# TC-001

| Campo | Contenido |
|---|---|
| **Identificador** | TC-001 |
| **Requisitos cubiertos** | Criterio del Avance 1: «Enviar un trabajo y obtener un ID único». RF/RNF: por asignar (ver [matriz](../verification-plan/matriz-trazabilidad.md)) |
| **Objetivo** | Comprobar de extremo a extremo que el CLI envía un trabajo al servicio por el socket Unix, recibe un ID y que dos envíos nunca reciben el mismo ID. |

## Precondiciones
1. Linux (Ubuntu 22.04 / 24.04) o WSL2 con Python 3.10 o superior.
2. Repositorio construido con `./scripts/setup.sh`.
3. Servidor y CLI integrados en la rama (`src/jobrunner/server.py` y `src/jobrunner/cli.py`).
4. Servicio en ejecución: `./scripts/run.sh` en una terminal (a mano). La automatización lo levanta sola, aislada, en un directorio temporal.

## Pasos
| # | Acción |
|---|---|
| 1 | En otra terminal, desde la raíz del repositorio: `export PATH="$PWD/scripts:$PATH"` (habilita `royito`). |
| 2 | Enviar un trabajo: `royito submit -- sleep 10`. Anotar el ID devuelto. |
| 3 | Enviar un segundo trabajo con el mismo comando y anotar su ID. |
| 4 | Consultar el primero: `royito status <id>`. |

## Resultado esperado
- Cada `submit` devuelve un ID.
- Los dos IDs son distintos.
- `status <id>` reconoce el ID devuelto y muestra su estado.

## Automatización
`verif/integration/test_tc001_enviar_trabajo.py` (servidor y CLI reales por socket Unix). Se ejecuta con `./scripts/test.sh` o `verif/scripts/verify.sh`. Cubre además RF-02 (comando vacío y JSON mal formado se rechazan sin tumbar el servicio). Complemento unitario: `verif/unit/test_ids_unicos.py` (2000 IDs sin repetir).

## Resultado observado
Ejecución `20261028-integracion`: 5 de las 6 pruebas pasan (el ID se devuelve, dos envíos dan IDs distintos, `status` reconoce el ID, el comando vacío se rechaza, una solicitud mal formada no tumba el servicio) y **1 falla**: `test_submit_exitoso_termina_con_codigo_0`. Un `submit` correcto devuelve el trabajo en JSON pero el CLI termina con **código de salida 1**, no 0.

Causa: `print_response()` en `src/jobrunner/cli.py` usa `"error" in response`, y el JSON de todo trabajo trae la clave `error` (con valor `null`), así que siempre lo trata como error. Registrado como **DEF-003** en la [matriz](../verification-plan/matriz-trazabilidad.md) (RF-17). Corrección sugerida: `if isinstance(response, dict) and response.get("error"):`.

La unicidad de IDs (antes DEF-001) pasa: `Job.new()` ya usa el UUID completo.
