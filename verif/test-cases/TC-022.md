# TC-022

| Campo | Contenido |
|---|---|
| **Identificador** | TC-022 |
| **Requisitos cubiertos** | Consistencia de la persistencia ante una interrupción durante una escritura (ADR-0002, riesgo «interrupción a mitad de una escritura»). RF/RNF: por confirmar contra el documento de requisitos (ver [matriz](../verification-plan/matriz-trazabilidad.md)) |
| **Objetivo** | Comprobar de forma repetible que, si el proceso muere con SIGKILL durante una escritura en SQLite, una escritura no confirmada no deja rastro, una confirmada sobrevive y la base queda íntegra y utilizable. |

## Precondiciones
1. Linux (Ubuntu 22.04 / 24.04) o WSL2 con Python 3.10 o superior.
2. Repositorio clonado. No se requiere el servicio en ejecución ni dependencias externas.

## Pasos
| # | Acción |
|---|---|
| 1 | Desde la raíz del repositorio: `./scripts/setup.sh`. |
| 2 | Ejecutar la verificación: `verif/scripts/verify.sh <run-id>` (o `PYTHONPATH=src python3 -m unittest discover -s verif/unit -v`). |
| 3 | En `unittest.log`, comprobar el resultado de las pruebas listadas abajo. |

Cómo se hace repetible: un proceso hijo abre la base, escribe y se mata a sí mismo con SIGKILL en un punto fijo (antes de confirmar la transacción, o justo después de confirmarla). La prueba lo repite 10 veces en cada modo y después reabre la base desde otro proceso. No depende de tiempos ni de azar.

## Resultado esperado
- Escritura sin confirmar: al reabrir, el trabajo conserva su estado anterior (RUNNING, sin código de salida) y no se pierde ni se duplica ninguna fila.
- Escritura confirmada: al reabrir, el nuevo estado (SUCCEEDED) está guardado.
- `PRAGMA integrity_check` devuelve `ok` en ambos casos.
- Tras la interrupción se puede seguir escribiendo en la base (por ejemplo, marcar el trabajo como FAILED durante la recuperación).
